# ForBirds API v1

Все маршруты относительны к origin форума. API использует PHP-сессию в cookie, не Bearer-токены. GET не меняет содержимое форума; все изменения — POST. На маршрутах `/api/…` HTML-разметка не генерируется; страницы `/`, `/index.html`, `/post.html`, `/dashboard.html`, `/profile.html` обслуживаются отдельно и подключены к API через `public/app.js`. Бинарные ответы — вложения, превью и аватарки.

## Общий формат

Успех:

```json
{"data":{"post_id":12,"thread_id":4,"status":"pending"}}
```

Ошибка:

```json
{"error":{"code":"forbidden","message":"Требуются права модератора."}}
```

### Язык системных ошибок

`Accept-Language: en` включает английские `error.message`, `ru` — русские.
Поддерживаются региональные варианты (`en-GB`) и веса `q`. Без поддерживаемого
языка используется русский. Ответы API содержат `Content-Language: en|ru`;
коды ошибок, HTTP-статусы, `retry_after`, права и данные не меняются.
Фронтенд отправляет язык явного выбора пользователя при каждом запросе.
Пользовательский контент не переводится. Для обработки ошибок используйте
`error.code`, не текст `error.message`.

Статусы: `200` успех, `201` создано, `400` неверный JSON, `401` нужен вход/неверные учётные данные, `403` нет прав/CSRF/бан, `404` нет объекта или он скрыт, `405` неподдерживаемый HTTP-метод, `409` конфликт, `413` превышен размер, `415` неверный Content-Type, `422` неверные поля, `429` лимит запросов (с `Retry-After`), `503` база ещё не установлена. Внутренние ошибки — общий `500`, детали только в серверном error log.

POST принимает `application/json`, `application/x-www-form-urlencoded` и `multipart/form-data`. Для обычной формы всё равно нужен JS или другой HTTP-клиент, который выставит заголовок `X-CSRF-Token`. Булевы значения: JSON `true/false`, числа `1/0` или строки `"1"/"0"`; строки `"true"` и `"false"` не принимаются. Ограничения длины строк указаны **в байтах UTF-8**.

Для **каждого POST**, включая вход, регистрацию и анонимную публикацию:

1. Выполните `GET /api/session`, сохраните cookie и `data.csrf_token`.
2. Передайте токен заголовком `X-CSRF-Token` вместе с той же cookie.
3. После входа, регистрации и выхода обновите токен из ответа — старый перестаёт действовать.

Поля, определяющие права автора (`role`, `auto_approve`, `user_id`, `status`), при публикации/регистрации клиент назначить не может. Права и статус вычисляются на сервере.

### Пагинация

Списки тем, ответов, сообщений профиля, своих сообщений, очереди и аудита:

```json
{"data":{"items":[],"page":1,"limit":20,"has_more":false}}
```

Query-параметры: `page` от 1, `limit` от 1 до 100 (большее значение ограничивается до 100). Списки разделов и публичный профиль не пагинируются.

## Сессия и аккаунты

| Метод | Маршрут | Поля / результат |
|---|---|---|
| GET | `/api/session` | `csrf_token`, `user` или `null` |
| POST | `/api/auth/register` | `username`, `password`; возвращает пользователя и новый CSRF, сразу выполняет вход |
| POST | `/api/auth/login` | `username`, `password`; возвращает пользователя и новый CSRF |
| POST | `/api/auth/logout` | `{}`; сбрасывает вход и возвращает новый CSRF |
| GET | `/api/flags` | Обнаруженные в `public/flags/` флаги: `file`, `code`, `label`, `url` |
| GET | `/api/users/{id}` | Профиль без хеша пароля. `auto_approve` виден только самому пользователю и персоналу |
| GET | `/api/users/{id}/posts` | Компактные темы и ответы с учётом прав, пагинация |
| GET | `/api/users/{id}/avatar` | Текущая аватарка JPEG либо 404; публична |
| POST | `/api/me/profile` | Своё описание и/или аватарка; сессия, CSRF, запрет для заблокированных |
| GET | `/api/me/posts` | Собственные сообщения, включая ожидающие, отклонённые и мягко удалённые; нужен вход |

Имя: 3–32 латинских буквы, цифры или `_`, уникальность без учёта регистра ASCII. Пароль: 12–72 байта, без NUL, хранится только хеш. Обрезки пробелов у пароля нет. Email и восстановление пароля пока не реализованы.

Поля пользователя в своей сессии: `id`, `username`, `role`, `auto_approve`, `is_banned`, `created_at`, `description`, `avatar_url`, `flag`. Внутренние `avatar_name` и `password_hash` не выдаются. Булевы поля из SQLite возвращаются как `0/1`. Время в UTC, ISO 8601.

## Профиль и настройки

`GET /api/users/{id}` возвращает публичные поля `id`, `username`, `role`, `is_banned`, `created_at`, `description`, `avatar_url`, `flag`. Своему аккаунту и персоналу дополнительно доступно `auto_approve`. Значение `avatar_url` — `/avatars/noavatar.png` либо `/api/users/{id}/avatar?v=VERSION`. Версия нужна для обновления отображения; эндпоинт всегда выдаёт **текущую** картинку, с `Content-Type: image/jpeg`, `nosniff` и `Cache-Control: no-store`. При отсутствии пользователя или своей аватарки — 404.

`GET /api/users/{id}/posts?page=1&limit=20` возвращает стандартную страницу `items/page/limit/has_more`, новые ID первыми. Каждая строка содержит `id`, `thread_id`, `is_root`, `status`, `created_at`, `excerpt` (первые 180 символов, не HTML), `title`, `section_id`, `url`. Полные тексты и вложения в этом списке отсутствуют. `url` указывает на нужную страницу темы (20 ответов на страницу с учётом видимости) и якорь сообщения. После изменения модерации положение ответа может измениться.

Гости и обычные посетители видят только `approved` при доступном исходном посте. Вошедший пользователь также видит свои `pending`, если сам исходный пост доступен ему по тем же правилам. Активные модераторы/администраторы видят все статусы, как при прямом просмотре темы. Для несуществующего пользователя — 404. Снятие роли/бан немедленно отменяет доступ персонала к скрытым чужим сообщениям.

`POST /api/me/profile` принимает:

- `description`: необязательная строка до **4000 байт UTF-8**, пробелы по краям обрезаются; пустая строка очищает описание. Отсутствующее поле сохраняет старое значение.
- `avatar`: необязательный **один файл** в multipart-форме, JPEG/PNG/GIF/WebP, максимум **2 МиБ**. Используйте имя поля `avatar`, не `files[]` и не `avatar[]`.
- `flag_file`: необязательное точное имя картинки из `GET /api/flags`, например `"RU.png"` или `"ru.gif"`. Пустая строка убирает флаг; отсутствие поля сохраняет прежний выбор. Несуществующий файл, путь или `null` — 422.
- `remove_avatar`: необязательный boolean, по умолчанию false. Удаляет прежнюю аватарку; одновременная загрузка файла недопустима (422).

Пример изменения только описания:

```json
{"description":"Наблюдаю за птицами в городе."}
```

Для файла отправляйте `multipart/form-data` с `avatar`, `description` и CSRF в заголовке. Сервер декодирует изображение через GD, проверяет габариты и бюджет памяти по правилам превью, затем сохраняет только JPEG до 256×256 без метаданных; GIF становится статичным. Оригинал не сохраняется. Файл находится в приватном `storage/avatars/` (не в кэше превью вложений), наружу доступен только через API. При замене/удалении старый файл удаляется. Описание и аватарка не меняются при ошибке проверки или записи БД.

Ответ — обновлённый объект своего профиля (не обёртка `user`). `user_id`, `id`, `role`, `auto_approve`, имена и пути файлов клиентом не назначаются. Чужой профиль через этот маршрут изменить нельзя: ID берётся из сессии, маршрута `/users/{id}/profile` нет. Для анонима — 401, неверного CSRF или бана — 403, не-картинки/повреждённого изображения — 422, большого файла — 413. Действует общий лимит POST; PoW и интервал публикации не затрагиваются. Описание и аватарка публичны и не входят в очередь модерации постов.

У деталей поста/ответа добавлено `avatar_url` автора, поэтому изменение картинки распространяется и на старые сообщения без копирования файлов. Анонимам возвращается стандартная аватарка.

Существующей установке требуется `php bin/console.php migrate` для `003_profiles.sql` и `004_profile_flags.sql`.

### Автоматический каталог флагов

`GET /api/flags` публичен, возвращает массив, например:

```json
{"data":[{"file":"RU.png","code":"RU","label":"Россия","url":"/flags/RU.png"}]}
```

Источником списка являются реальные PNG/GIF/JPEG/WebP в корне `public/flags/`. Имена: `[A-Za-z0-9][A-Za-z0-9_-]{0,63}` плюс расширение (регистр расширения не важен). Вложенные папки, симлинки, скрытые и неподдерживаемые файлы пропускаются. На каждом HTTP-запросе каталог читается заново, поэтому добавление/удаление файла не требует изменения кода или перезапуска.

Необязательный UTF-8-словарь `public/flags/flags.json` имеет вид `{"RU":"Россия"}`. Ключ совпадает с `code` (исходное имя без расширения), включая регистр. Без непустой строки-перевода `label` равен `code`; отсутствие/повреждение JSON не мешает выдаче картинок. Записи словаря без файлов не создают варианты выбора. Слишком большой словарь (больше 1 МиБ) пропускается. Метаданные доступны через API, прямой маршрут JSON не требуется.

Публичный профиль/сессия и детали поста/ответа содержат `flag`: объект такого же вида или `null`. Внутреннее поле БД `flag_file` отдельно не раскрывается, выбранный файл доступен как `flag.file`. Анонимам и пользователям без флага возвращается `null`. Если файл был удалён, тоже возвращается `null`, а не URL сломанной картинки. Выбор меняется только через свой `POST /api/me/profile` с обычными проверками сессии/CSRF/бана; чужой выбор изменить нельзя. Изменение распространяется и на старые сообщения.

## Разделы

| Метод | Маршрут | Доступ |
|---|---|---|
| GET | `/api/sections` | Все |
| POST | `/api/sections` | Администратор |
| POST | `/api/sections/{id}/settings` | Администратор |

`GET /api/sections` дополнительно возвращает `recent_posts` для каждого раздела, включая пустой массив для раздела без доступных сообщений. В нём до пяти новейших по ID тем/ответов: `id`, `thread_id`, `section_id`, `title`, `is_root`, `username` (null для анонима), `status`, `created_at`, `excerpt` (до 100 символов), `url`. Ссылка ведёт к сообщению на нужной странице темы (20 ответов на странице с учётом видимости).

Обычным посетителям выдаются только `approved` при исходном посте `approved`; активному персоналу — `approved`/`pending` при исходном посте с одним из этих статусов. `rejected`/`deleted` не участвуют. Фильтрация выполняется **до** выбора пяти сообщений, поэтому скрытые записи не вытесняют доступные. Обновлённые права сессии применяются на каждом запросе. Это блок раздела, а не замена `/api/me/posts`. Для выборки используется SQLite 3.25+ (оконная функция); запросы не размножаются по числу разделов.


Создание:

```json
{"slug":"general","title":"Общий раздел","description":"Обсуждение форума"}
```

`slug`: 1–64 байта, строчные латинские буквы/цифры с одиночными дефисами между группами. `title`: 1–200, `description`: 0–4000, необязательно.

Настройки: любое подмножество `title`, `description`, `is_archived`. `slug` после создания не меняется. Архивный раздел доступен для чтения, обычные авторы не могут создавать там темы и ответы; персонал может.

## Локальная хэш-капча и интервалы

Проверка обязательна для **каждой темы и ответа, для всех ролей**. Это локальный proof-of-work, не Cloudflare Turnstile и не доказательство человечности. Создание разделов, вход и действия модератора не требуют PoW (но требуют CSRF/прав и ограничены по частоте).

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/posting-status` | `interval_seconds`, `retry_after`, `next_allowed_at` (Unix UTC или 0), `pow_required:true` |
| POST | `/api/pow/challenge` | Выдать одноразовую задачу, тело `{}`, нужен CSRF |

Интервал между принятыми сообщениями: **45 секунд для анонимов, 30 секунд для всех аккаунтов**, включая доверенных, модераторов и администраторов. Темы и ответы разделяют один лимит. Анонимный ключ — HMAC `REMOTE_ADDR`, пользовательский — HMAC ID аккаунта. Новая cookie/вкладка/повторный вход не сбрасывают активный интервал; анонимы за одним IP разделяют лимит. Передача `X-Forwarded-For` клиентом его не меняет.

Пока интервал не окончен, выдача задач и публикация возвращают `429`, `error.code: "posting_cooldown"`, `error.retry_after` и HTTP `Retry-After` с оставшимися секундами. Отсчёт начинается после успешного принятия сообщения, даже если оно ожидает модерации.

Задача:

```json
{"data":{"id":"32-hex-characters","prefix":"64-hex-characters","difficulty":18,"expires_at":1795694400,"algorithm":"sha256","format":"prefix:nonce","interval_seconds":45}}
```

Строки ID/prefix в этом примере описательные; реальные значения — случайный lowercase hex. Решение — десятичная строка `nonce` без ведущих нулей (кроме `"0"`), до 16 цифр. Нужно подобрать её так, чтобы SHA-256 от **UTF-8 строки `prefix + ":" + nonce`** начинался с `difficulty` нулевых **битов**, не hex-символов. Это проверяет PHP, а не доверяет флагу от клиента. Worker/реализация SHA-256 уже находятся в `public/pow-worker.js` и `public/sha256.js`.

Передавайте при создании темы/ответа в JSON или FormData:

```json
{"pow_id":"<id задачи>","pow_nonce":"<найденное число>"}
```

Особенности:

- Срок задачи 300 с. Новая задача заменяет предыдущую для той же сессии/автора; разные вкладки одной сессии могут сделать старое решение неактуальным.
- Привязка к PHP-сессии и субъекту лимита. Вход/выход, другая сессия или другой анонимный IP делают чужое решение непригодным.
- Решение одноразовое; его потребление, занятие интервала и запись сообщения атомарны. Ошибка публикации откатывает их вместе.
- Задача должна быть выдана после окончания предыдущего интервала. Предварительно запасённые в других сессиях задачи нельзя использовать после следующего сообщения.
- Ошибки `422`: `pow_required` (нет/неверный формат полей), `pow_invalid` (неверный хэш), `pow_expired` (срок, повторное использование, неверная привязка или устаревшая задача).
- Задачи: до 20/мин на IP, дополнительно к общим лимитам POST/публикаций. CSRF требуется и анонимам.
- `FORBIRDS_POW_DIFFICULTY` на сервере: 8–24 бита, по умолчанию 18. Клиент не выбирает сложность. Время решения вероятностное и зависит от процессора; мощные боты тоже могут решать задачи.

## Темы и ответы

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/threads` | Для посетителей — одобренные темы; для модераторов/администраторов — одобренные и ожидающие проверки |
| GET | `/api/threads/{id}` | Тема, исходный `post` и пагинированные `replies` |
| GET | `/api/posts/{id}` | Одно доступное сообщение с вложениями |
| POST | `/api/threads` | Создать тему и её исходное сообщение атомарно |
| POST | `/api/threads/{id}/replies` | Создать ответ без заголовка |
| POST | `/api/threads/{id}/settings` | Настройки темы; модератор/администратор |

Создание темы:

```json
{"section_id":1,"title":"Первая тема","body":"Текст сообщения","pow_id":"<id>","pow_nonce":"<решение>"}
```

Ответ:

```json
{"body":"Текст ответа","pow_id":"<id>","pow_nonce":"<решение>"}
```

`title`: 1–200, `body`: 1–50000 байт, пустые/пробельные значения не допускаются. Текст — **обычный текст**, не HTML и не BBCode. На фронтенде используйте `textContent` (и CSS `white-space: pre-wrap`), не `innerHTML`.

Ответ на создание: `post_id`, `thread_id`, `status`. `№` в интерфейсе — `post_id`, глобально уникальный для тем и ответов. Автоматические статусы:

| Автор | Статус |
|---|---|
| Аноним / обычный пользователь | `pending` |
| Пользователь с `auto_approve=1` | `approved` |
| Модератор / администратор | `approved` |

Клиент не может запросить одобрение собственным полем `status`. Автор аккаунта видит свои `pending`-публикации в `/api/me/posts` и по ID, но они не появляются в публичном списке. Анонимное ожидающее сообщение доступно только персоналу, даже в сессии отправителя.

### Главная, новости, поиск

Фильтры `GET /api/threads` можно совмещать:

- `?section_id=1` — раздел;
- `?featured=1` — главная;
- `?news=1` — новости/обновления;
- `?q=слово` — поиск подстроки в заголовке или **одобренных** сообщениях (для персонала также в `pending`), без учёта регистра Unicode; 2–200 байт;
- `?limit=20&page=2` — пагинация.

Для обычных посетителей темы сортируются по последнему действующему бампу, затем по ID; ответы — от старых к новым. Для персонала сначала идут темы с исходным постом `pending`, затем одобренные темы с непроверенными ответами, затем остальные; внутри групп — по последнему действующему бампу, затем новые ID первыми. Ожидающие темы видны модераторам/администраторам в обычном `/api/threads`, в разделах, поиске и при совпадении фильтров `news`/`featured`. Клиентские флаги не расширяют права обычного пользователя. Отклонённые и удалённые исходные посты не попадают в эти списки.

В списке возвращается `status` исходного поста. `reply_count` для посетителей считает только одобренные ответы, для персонала — одобренные плюс ожидающие. Поле `pending_reply_count` показывает персоналу число непроверенных ответов, всем остальным возвращает **0**, чтобы не раскрывать скрытую активность. Поиск посетителей не учитывает текст непроверенных ответов. В `/api/threads/{id}` персонал уже видит все статусы ответов и может модерировать их по ID.

Фронтенд для персонала на главной не передаёт `featured=1`, поэтому все активные темы доступны сразу, с пометками и кнопками модерации. Для обычного посетителя сохраняется `featured=1`. Одобрение ответа не делает публичной тему со скрытым исходным постом; публичная выдача по-прежнему требует одобрения исходного сообщения.

При создании темы персонал может передать `is_news`, `is_featured`. Обычный пользователь получает `403`, если пытается включить эти отметки.

Настройки темы: любое подмножество `is_locked`, `is_news`, `is_featured`. В закрытую тему обычные авторы не отвечают, персонал может. Эти настройки не заменяют одобрение исходного поста.

## Вложения

При создании темы или ответа вместо JSON отправьте `FormData`:

- обычные поля `section_id`, `title`, `body` (для ответа только `body`), а также `pow_id` и `pow_nonce`;
- до 10 файлов в `files[]`;
- необязательный массив `spoilers[]` — индексы файлов, начиная с 0.

Лимиты: 5 МиБ на файл, 20 МиБ суммарно. Разрешены JPG/JPEG, PNG, GIF, WebP, MP4, WebM, MP3/MP2, FLAC, WAV, OGG/OGA/Opus, M4A/M4B, AAC, AIFF/AIF, WMA, WEBA, TXT, PDF и ZIP. Проверяются MIME через `fileinfo` и соответствие расширению. Изображения дополнительно проверяются по заголовку и габаритам: каждая сторона не более 12000 px и не более 40 млн пикселей. Исполняемые файлы, HTML и SVG не принимаются. Архивы не распаковываются; наличие допустимого MIME не означает отсутствие вредоносного содержимого.

`GET /api/posts/{id}` возвращает `attachments`:

```json
[{"id":3,"original_name":"photo.jpg","mime_type":"image/jpeg","byte_size":1024,"spoiler":1,"is_image":true,"is_video":false,"download_url":"/api/attachments/3/download","view_url":"/api/attachments/3/view","preview_url":"/api/attachments/3/preview"}]
```

`GET /api/attachments/{id}/download` проверяет доступ **к сообщению и исходному посту темы**. До одобрения файл доступен только персоналу и зарегистрированному автору ожидающего сообщения. После снятия одобрения доступ снова закрывается. Физический путь, случайное имя файла на диске и прямой публичный URL не раскрываются.

Маршруты для вложений:

| GET | Результат |
|---|---|
| `/api/attachments/{id}/download` | Оригинальные байты, `application/octet-stream`, `Content-Disposition: attachment` |
| `/api/attachments/{id}/view` | PNG/GIF/JPEG/WebP, MP4/WebM и поддержанное аудио: оригинальные байты с соответствующим MIME и `Content-Disposition: inline` |
| `/api/attachments/{id}/preview` | Только изображения: JPEG-превью ≤256×256, `image/jpeg`, `Content-Disposition: inline` |

Все три маршрута сначала проверяют доступ к сообщению **и исходному посту**, даже если JPEG уже есть в кэше. Отправляют `nosniff`, `no-store` и ограничительную CSP; относительные URL не раскрывают пути на диске. Для TXT/PDF/ZIP `is_image:false`, `is_video:false`, `preview_url:null`, `view_url:null`; запросы `/view` и `/preview` по их ID возвращают `404`, а не отображают произвольный HTML.

Для изображений нужен PHP GD с поддержкой JPEG/PNG/GIF/WebP. При загрузке происходит полное декодирование, ресемплинг с сохранением пропорций и запись JPEG (качество 85), без увеличения маленьких изображений. Прозрачный фон становится белым; GIF-превью — первый кадр, но исходная анимация при `/view` и `/download` не меняется. Производные JPEG хранятся приватно в `storage/previews/`; для старых вложений/потерянного кэша создаются лениво при авторизованном запросе. Миграция схемы не нужна.

Дополнительные ошибки: `503 image_processing_unavailable` — нет нужного GD-кодека; `422 invalid_image` — не удалось декодировать; `413 image_memory_limit` — габариты не укладываются в бюджет памяти PHP. Ошибки загрузки откатывают пост, оригиналы/превью, PoW и таймер одной транзакцией.

Фронтенд отображает обычные изображения через `<img src="preview_url">` в ссылке на `view_url`; рядом отдельная ссылка `download_url`. Обычное нажатие открывает оригинал в модальном `<dialog>` поверх страницы, без перехода и без новой вкладки. Изображение ограничено размером окна, GIF сохраняет анимацию. Предусмотрены закрытие кнопкой/Escape/фоном, возврат фокуса, сообщение об ошибке и скачивание.

При `spoiler:1` в `src` картинки подставляется **`/static/preview/spolier.png`**, исходный файл макета, а не настоящее превью. До открытия оригинал и настоящее превью скрытой картинки не запрашиваются. Это визуальное скрытие, не отдельное право доступа: авторизованный читатель может запросить одобренное вложение по API.

### Видео и потоковая выдача

Для MP4/WebM метаданные содержат `is_video:true`, `is_image:false`, `preview_url:null`, `view_url` с оригинальным видео и `download_url`. MIME — `video/mp4`/`video/webm`, допустимые расширения — `.mp4`/`.webm`. MIME определяется сервером, а не полем браузера. Поддельная картинка/HTML с расширением видео отклоняется. Контейнер проверяется по MIME, но полное декодирование и транскодирование не выполняются; воспроизводимость кодека зависит от браузера.

`/view` возвращает правильный MIME и `Content-Disposition: inline`, `/download` — `application/octet-stream` и `attachment`. `/preview` для видео — 404. Фронтенд использует `<video controls playsinline preload="none">`, без автозапуска. Для видео под спойлером элемент с `src` создаётся только после раскрытия; при сворачивании ставится на паузу. Скачивание оригинала доступно и при неподдерживаемом кодеке. CSP страниц разрешает `media-src 'self'`, внешних плееров/iframe нет.

У маршрутов вложений `/view`, `/download`, `/preview` поддержан **HEAD** с теми же проверками доступа и заголовками, но без тела. Другие API остаются GET/POST. GET поддерживает один `Range: bytes=START-END`, `bytes=START-` или `bytes=-SUFFIX`:

- валидный диапазон: **206**, `Content-Range: bytes START-END/SIZE`, точный `Content-Length`, `Accept-Ranges: bytes`;
- неверный/недостижимый/множественный диапазон: **416**, `Content-Range: bytes */SIZE`, пустое тело;
- HEAD игнорирует Range и возвращает длину полного представления;
- с `If-Range` возвращается полное представление (200), поскольку сервер не выпускает валидаторы;
- проверка сообщения и его родителя выполняется **до** обработки диапазона: скрытому вложению возвращается 404 даже при неверном Range, не раскрывая длину.

Бинарная передача идёт частями, с закрытой блокировкой PHP-сессии и `Cache-Control: no-store`. Исходные байты файлов не меняются. Лимиты остаются 5 МиБ/файл, 20 МиБ/пост, 10 файлов. Новая миграция для видео и `recent_posts` не требуется. Редактирования публикаций и дозагрузки файлов после создания пока нет.

## Модерация

| Метод | Маршрут | Доступ |
|---|---|---|
| GET | `/api/moderation/queue` | Модератор/администратор |
| GET | `/api/moderation/audit` | Модератор/администратор |
| POST | `/api/posts/{id}/moderate` | Модератор/администратор |
| POST | `/api/users/{id}/trust` | Модератор/администратор |
| POST | `/api/users/{id}/ban` | Модератор/администратор |
| POST | `/api/users/{id}/role` | Только администратор |

Модерация поста:

```json
{"action":"approve","reason":"Проверено"}
```

Действия:

- `approve` → `approved`;
- `unapprove` → `pending`, убрать из публичного доступа;
- `reject` → `rejected`;
- `delete` → `deleted`, без API-восстановления. Файлы не удаляются физически, но доступ к ним закрывается.

`reason` необязателен, до 1000 байт. Переходы между `pending`, `approved`, `rejected` разрешены; `deleted` — конечный статус. Одобрение происходит для конкретного сообщения, а не всей темы.

Автоподтверждение и бан:

```json
{"enabled":true,"reason":"Доверенный участник"}
```

Отключение: `enabled:false`. Автоподтверждение действует только на **будущие** сообщения, не меняет старую очередь. Блокировка запрещает вход и любые POST, кроме выхода, в том числе для уже открытой сессии. Ранее одобренные сообщения забаненного остаются опубликованными; в сообщении/профиле есть признак бана для отображения интерфейсом.

Модератор управляет только обычными пользователями. Администратор также может управлять модераторами. Нельзя через эти маршруты менять самого себя или администратора. Назначение роли:

```json
{"role":"moderator","reason":"Назначение модератора"}
```

Допустимы `user` и `moderator`. Администратор создаётся только локальной CLI-командой, повысить себя через регистрацию/POST невозможно. Роль модератора сама даёт немедленную публикацию; при понижении отдельный ранее выданный `auto_approve` сохраняется (при необходимости отзовите отдельно).

Очередь содержит только `pending`, порядок от старых к новым. Для просмотра вложений сообщения из очереди используйте `/api/posts/{id}`. Персонал также может читать отклонённые и мягко удалённые сообщения по ID для разбирательств.

Изменения статусов, доверия, банов, ролей, разделов и настроек тем пишутся в `audit_log` в одной транзакции с изменением. Аудит доступен только персоналу; включает исполнителя, действие, объект, время и подробности.

## Пример подключения фронтенда

Рабочий интерфейс уже использует отдельный `public/app.js`, не PHP-шаблоны. Ниже сокращённый пример HTTP-клиента; вычисление PoW выполняйте Worker-ом после проверки `/posting-status`:

```js
let csrf;

async function api(path, { method = 'GET', body } = {}) {
  const headers = {};
  if (method === 'POST') headers['X-CSRF-Token'] = csrf;
  if (body !== undefined && !(body instanceof FormData)) {
    headers['Content-Type'] = 'application/json';
    body = JSON.stringify(body);
  }
  const response = await fetch(`/api${path}`, {
    method, headers, body, credentials: 'same-origin'
  });
  const result = await response.json();
  if (!response.ok) throw new Error(result.error.message);
  if (result.data?.csrf_token) csrf = result.data.csrf_token;
  return result.data;
}

function solveChallenge(challenge) {
  return new Promise((resolve, reject) => {
    const worker = new Worker('/pow-worker.js');
    worker.onmessage = ({ data }) => {
      if (data.type === 'solved') { worker.terminate(); resolve(data.nonce); }
      else if (data.type === 'error') { worker.terminate(); reject(new Error(data.message)); }
    };
    worker.onerror = () => { worker.terminate(); reject(new Error('Ошибка Worker')); };
    worker.postMessage(challenge);
  });
}

await api('/session');
await api('/auth/login', {
  method: 'POST',
  body: { username: 'admin', password: passwordInput.value }
});

const section = await api('/sections', {
  method: 'POST', body: { slug: 'general', title: 'Общий раздел' }
});

// solveChallenge запускает /pow-worker.js и возвращает nonce из сообщения type=solved.
const challenge = await api('/pow/challenge', { method: 'POST', body: {} });
const nonce = await solveChallenge(challenge);
const result = await api('/threads', {
  method: 'POST',
  body: { section_id: section.id, title: 'Привет', body: 'Первая тема', pow_id: challenge.id, pow_nonce: nonce }
});

// Загрузка выполняется ОДНИМ запросом с созданием сообщения.
// Это СЛЕДУЮЩАЯ публикация: дождитесь interval, получите НОВУЮ задачу и решите её.
const status = await api('/posting-status');
await new Promise(resolve => setTimeout(resolve, status.retry_after * 1000));
const fileChallenge = await api('/pow/challenge', { method: 'POST', body: {} });
const fileNonce = await solveChallenge(fileChallenge);
const form = new FormData();
form.append('pow_id', fileChallenge.id);
form.append('pow_nonce', fileNonce);
form.append('section_id', section.id);
form.append('title', 'Тема с файлом');
form.append('body', 'Текст');
form.append('files[]', fileInput.files[0]);
form.append('spoilers[]', '0');
await api('/threads', { method: 'POST', body: form });
// Content-Type для FormData браузер выставляет сам вместе с boundary.
```

В реальном интерфейсе перехватывайте ошибки, не храните пароль после входа, показывайте сообщение о премодерации при `status === 'pending'`. Ссылки на скачивание берите из `download_url`. Нельзя вызывать `response.json()` для успешного бинарного скачивания — используйте обычную ссылку или `response.blob()`.

Все POST ниже требуют обычную cookie-сессию и CSRF-токен. Новые действия требуют
непустую `reason` (1–1000 байт UTF-8), кроме переключения приватности.
Изменения журналируются. GET списка блокировок и архива поддерживает обычную пагинацию.

| Метод | Маршрут | Доступ и поля |
|---|---|---|
| POST | `/api/posts/{id}/move` | Персонал: для корня темы `section_id`, для ответа `thread_id`, `reason`. Сохраняет ID, автора, статус и вложения. Возвращает `post_id`, `thread_id` |
| POST | `/api/attachments/{id}/moderate` | Персонал: `action` = `spoiler`, `unspoiler`, `hide`, `show`, `delete`, `hashban`; `reason` |
| GET | `/api/moderation/archive` | Персонал: отклонённые и удалённые посты; не открывает их посетителям |
| GET | `/api/moderation/media-bans` | Персонал: ID запрета, причина, автор и дата (без оригинала файла) |
| POST | `/api/moderation/media-bans/{id}/remove` | Персонал, `reason`; снятие запрета не восстанавливает физически удалённые файлы |
| POST | `/api/moderation/privacy` | Только администратор: `enabled` (bool); переключатель действует на текущую сессию |
| GET | `/api/posts/{id}/identity` | Только администратор с включённым показом: `ip`, `cid`, `hid` или `null`. Каждый успешный просмотр записывается в `privacy_access` |
| GET | `/api/moderation/identity-bans` | Только администратор с включённым показом; содержит чувствительные сведения о сетях и идентификаторах |
| POST | `/api/moderation/identity-bans` | Только администратор с включённым показом: `kind` = `cidr`, `browser`, `fingerprint`; `hours` 1–8760 (по умолчанию 24), `reason`; для `cidr` — `value` с IP/CIDR, иначе `post_id` |
| POST | `/api/moderation/identity-bans/{id}/remove` | Только администратор с включённым показом, `reason` |

### Вложения и запреты

Посты персонала содержат `attachments[].moderation_state` (`visible`, `hidden`,
`deleted`) и `blocked`. У скрытых, удалённых и заблокированных файлов URL равны
`null`; обычным читателям такие вложения вообще не выдаются. Их прямые
`download`, `preview`, `view`, `HEAD` и Range-запросы недоступны **всем**, включая персонал.
`spoiler` — только визуальное предупреждение: прямой URL остаётся доступен.

`delete` безвозвратно удаляет оригинал и производное превью, сохраняя запись
в БД и журнал. `hashban` сохраняет отпечатки, затем так же удаляет выбранный
оригинал и превью. Точные и похожие совпадения среди других вложений сразу
перестают отдаваться через API. Для физического удаления остальных совпадений
есть отдельная команда `purge-banned-media`.

SHA-256 сравнивает байты файлов всех поддерживаемых типов. Для JPEG/PNG/GIF/WebP
дополнительно сравниваются 256-битные dHash и aHash: расстояние Хэмминга не более
8 и 12 бит соответственно. Отпечатки изображений вычисляются после композиции
прозрачности на белом фоне. **Только первый декодированный кадр**, без семантической
классификации. Небольшие изменения часто распознаются, но не гарантированно:
возможны обходы и ложные совпадения (особенно однотонных изображений).
Для видео/архивов — только точное совпадение, не сравнение кадров/содержимого архива.
Аватарки проверяются при загрузке и выдаче; публичные статические ресурсы сайта
не являются пользовательскими загрузками и в denylist не входят.

### Бамп и sage

`POST /api/threads/{id}/replies` принимает `sage` (bool, по умолчанию false).
Опубликованный ответ без sage поднимает тему в ленте. Ожидающий проверки ответ
поднимает её только при подтверждении. Повторное подтверждение уже опубликованного
поста не поднимает тему снова. Удаление/отзыв подтверждения исключает его вклад
в сортировку. Корневая публикация задаёт начальный бамп; sage относится к ответам.
Перемещение ответа переносит его существующий порядок бампа, не создавая нового.
Приоритеты очереди ожидающих тем/ответов у персонала сохранены поверх бамп-сортировки.

### IP, cookie ID и отпечаток браузера

Обычные ответы API никогда не содержат `author_ip`, `browser_id`, `fingerprint`,
даже у персонала. `/api/session` дополнительно возвращает `privacy_enabled`.
Переключатель — **проверка на сервере**, а не CSS-скрытие уже полученных IP.
Данные старых публикаций до миграции отсутствуют (`null`).

IP берётся только из `REMOTE_ADDR`. Заголовки `X-Forwarded-For` клиенту не доверяются;
настройте real-IP доверенного proxy в Nginx. Поддерживаются IPv4 и IPv6 CIDR.
Cookie `__Host-forbirds_browser` (на HTTP-разработке `forbirds_browser`) — случайный подписанный HttpOnly/SameSite ID на 180 дней,
не аппаратный идентификатор. Клиент отправляет необязательный
`X-ForBirds-Fingerprint` (SHA-256 от Canvas/WebGL/параметров браузера);
сервер сохраняет только site-local HMAC. Исходные canvas/GPU-строки не отправляются.
Идентификаторы `cid`/`hid` в административном API — эти HMAC, не исходные сигналы.

Сигналы можно сбросить/подделать; схожие конфигурации дают совпадения. Отсутствующий
отпечаток не блокирует API-клиентов или privacy-браузеры. Это дополнительная мера,
не доказательство личности и не гарантия против обхода бана. При совпадении
активного сетевого/cookie/fingerprint-бана обычному клиенту запрещены POST, кроме
входа/выхода. Персонал освобождён от этих банов для восстановления управления;
бан самого аккаунта по-прежнему действует. Причина сетевого бана публично не раскрывается.

Сайт показывает уведомление о сборе антиспам-сигналов. Для ограничения хранения
владелец должен запускать `prune-identities` ежедневно: очищаются IP/CID/HID постов
старше 30 дней, старые записи доступа и истёкшие баны. Без запуска этой команды
автоматического TTL нет. Активные баны и отпечатки файлов сохраняются отдельно.
Учтите также сроки хранения резервных копий, cookies и access-логов веб-сервера.

## Модерация профилей и ограничения постов (миграция 006)

| Метод | Маршрут | Поля / права |
|---|---|---|
| POST | `/api/users/{id}/profile/moderate` | Персонал: `action` и обязательная `reason` |
| GET | `/api/moderation/description-bans` | Персонал: пагинация запретов описаний, без текста и его хэша |
| POST | `/api/moderation/description-bans/{id}/remove` | Персонал, обязательная `reason` |
| POST | `/api/posts/{id}/restrict` | Персонал: `action` = `hide`, `unhide`, `block`, `unblock`; обязательная `reason` |
| GET | `/api/moderation/restricted` | Персонал: пагинация скрытых и заблокированных постов |

### Профили

Действия: `avatar_delete`, `avatar_hashban`, `avatar_lock`, `avatar_unlock`,
`description_delete`, `description_hashban`, `description_lock`, `description_unlock`.
Модератор может изменять профиль обычного участника; администратор — также
модератора. Нельзя модерировать свой профиль или профиль администратора этим
endpoint: для своего профиля есть обычное редактирование.

Удаление аватарки очищает ссылку и удаляет сохранённый JPEG. `avatar_hashban`
сначала добавляет SHA-256 и перцептивные отпечатки JPEG в **общий список запретов
файлов**, затем удаляет аватарку. Совпадения блокируются и при последующих
загрузках вложений/аватарок, и при выдаче существующих совпадений. Ограничения
перцептивного сравнения из предыдущего раздела сохраняются.

Удаление описания очищает поле. `description_hashban` запрещает совпадающий
нормализованный текст для **всех профилей**, затем очищает выбранное описание.
Нормализация: нижний регистр, последовательности Unicode-пробелов/переносов и
ряда zero-width символов приводятся к одному пробелу, края обрезаются.
Сохраняется SHA-256 нормализованного текста, не оригинал. Пустое описание
запретить нельзя. Уже существующие совпадающие описания не выдаются в профилях
и `/api/session`, хотя у других пользователей запись в БД остаётся.
Это не семантическое сравнение: опечатки, похожие буквы и перефразирование могут
обойти запрет. Снятие запрета может снова сделать существующие копии видимыми;
очищенное описание выбранного пользователя автоматически не восстанавливается.

Блокировки редактирования `avatar_locked`, `description_locked` независимы от
удаления/хэшбана и возвращаются только владельцу профиля и персоналу. Закрытое
поле нельзя изменить через `/api/me/profile`, включая прямые API-запросы и
ранее открытую форму; ответ `403 profile_locked`. Остальные поля менять можно.
Запрещённый текст даёт `422 description_banned`. Персонал может очистить поле
даже при блокировке и затем явно разрешить его редактирование.

### Посты

`is_hidden` и `is_blocked` — независимые флаги, не замена статуса премодерации.
Оба скрывают пост **от всех, кроме персонала**, включая автора. Ограничение
исходного поста закрывает всю тему и её вложения. Учитываются прямые запросы,
ленты, поиск, новости, последние сообщения разделов, профили, свои сообщения,
число ответов, пагинация и бамп. Персоналу доступны карточки и отдельный список
ограниченных постов; скрытый/заблокированный текст не попадает обычным клиентам.
Вложения ограниченного поста доступны персоналу, если сами файлы не скрыты,
не удалены и не запрещены общим списком файлов.

`block` дополнительно запрещает подтверждение поста до `unblock` (`409 post_blocked`).
`unhide` не снимает блокировку, `unblock` не снимает скрытие. Снятие последнего
ограничения возвращает обычные правила видимости и прежний вклад в бамп; оно
само по себе не подтверждает пост и не создаёт новый бамп. Удалённый пост не
восстанавливается снятием ограничений. Все новые действия журналируются с причиной.

### Переименование флагов

Пять файлов с пробелами/апострофом переименованы в безопасные имена:
`apeson.png`, `Cyber-Israel.png`, `Gem-Pass.png`, `Great-Britain.png`, `I-was-raped.png`.
Содержимое картинок не изменено; исходные читаемые подписи находятся в `flags.json`.
Миграция 006 обновляет старые ссылки `users.flag_file`, если они были заданы вручную.
Allowlist путей не расширяется.


## Аудиовложения и цитаты

Метаданные каждого вложения дополнены `is_audio: boolean`. У аудио:
`is_audio:true`, `is_video:false`, `is_image:false`, `preview_url:null`,
`view_url:/api/attachments/{id}/view`; отдельный `download_url` сохранён.
Поддержаны расширения mp3/mp2, flac, wav, ogg/oga/opus, m4a/m4b, aac,
aif/aiff, wma и weba. Сервер сверяет расширение с MIME из fileinfo; список
допустимых пар находится в `MediaFile::AUDIO_TYPES`. MP4/WebM-контейнеры с
аудиорасширением классифицируются как аудио, а не видео. Анализ каждого трека
и проверка декодируемости кодека не выполняются.

`mime_type` хранит исходный результат fileinfo. При `/view` используются
браузерные MIME-эквиваленты: например, audio/x-wav → audio/wav,
audio/x-m4a или video/mp4 с расширением m4a → audio/mp4,
video/webm с расширением weba → audio/webm. Байты остаются исходными.
`/view` поддерживает GET/HEAD и single-byte Range так же, как видео;
`/preview` для аудио возвращает 404. Авторизация поста/корня, запреты файлов,
скрытие и блокировки проверяются до выдачи любого диапазона.
`/download` по-прежнему возвращает attachment с application/octet-stream.
Нет автозапуска, внешних плееров и серверного транскодирования. Кодеки,
не поддерживаемые браузером, остаются доступны для скачивания.

Цветные цитаты — только безопасное представление `body` на клиенте. Первый
символ строки `>` задаёт зелёный цвет, `<` — оранжевый, `^` — голубой.
Символы и переносы сохраняются; API по-прежнему принимает и возвращает простой
текст, не HTML. К существующим постам применяется тот же рендерер без миграции.

## Read-only network policy and reactions (migration 007)

Tor exit addresses / known I2P gateway networks are imported by an operator;
trusted tunnel ingress can supply a non-HTTP server marker. Setup, updates,
limitations and recovery: [NETWORK_ACCESS.md](NETWORK_ACCESS.md).
Every POST is denied with `403 network_read_only` for a recognized connection or
its persisted browser/account write ban. This is checked after CSRF validation
and before endpoint side effects; staff are not exempt. A valid write attempt
from a recognized connection automatically records browser + current account
restrictions. GET/HEAD remain subject to normal authorization, not write bans.
`GET /api/session` now includes `read_only: boolean`.

| Method | Route | Contract |
|---|---|---|
| GET | `/api/reactions` | Array of available `{file,label,url}` raster reaction images |
| GET | `/api/posts/{id}/reactions` | Visibility-protected reaction summary, also included as `post.reactions` |
| POST | `/api/posts/{id}/reactions` | Signed-in user + CSRF, `{reaction:"like.png"}` replaces their reaction; `{reaction:""}` removes it |
| GET | `/api/moderation/network-bans` | Admin + enabled identity privacy checkbox; paginated current restrictions |
| GET | `/api/moderation/network-ban-events` | Admin + privacy checkbox; paginated add/remove event history |
| POST | `/api/moderation/network-bans/{id}/remove` | Admin + privacy checkbox + CSRF + nonempty `reason` |

Summary items contain `{file,label,url,count,selected}`. Counts expose no voter
identities; `selected` is only the current user's own state. One reaction per
user per post, repeated assignment is idempotent; click on the selected reaction
sends an empty string to remove it. The UI shows only positive-count reactions
under the post, with a separate **+** button opening an accessible chooser. The
API still returns the complete catalog including zero counts so unused reactions
remain selectable; the chooser itself shows images/labels, not zero counters.
Escape, Close and backdrop dismiss it; a successful selection closes it and returns
focus to the + button. Guests/read-only users cannot open the chooser or vote.
No new migration is needed for this presentation change.
No PoW/cooldown for reactions, but the existing
IP write rate-limit and a dedicated 30 reaction requests/minute/IP limit apply.
Ordinary account/identity/network bans all apply. Guests may see counts, not vote.
Only approved posts with an approved thread root accept reactions. Locked threads
and archived sections reject writes with `409 reactions_unavailable`; hidden/
blocked posts or roots reject ordinary visitors with 404, including the summary
endpoint. Staff visibility alone does not permit reacting to unpublished posts.
Votes do not change bump order or create post revisions.

Reaction images are operator assets in `public/static/reactions` (PNG/GIF/JPEG/WebP,
2 MiB, max 512×512, up to 128; same safe filename pattern as flags). No visitor
uploads, SVG or symlinks. Optional `reactions.json` maps filename stems to labels.
Missing/removed images disappear from summaries without deleting votes; re-adding
the file restores counts. README/dictionary/invalid files are not served by the
PHP static router. Three original basic icons (like, heart, laugh) are included and may be replaced.

## Admin attribution / falseflag and Markdown (migration 008)

Existing POST `/api/threads` and `/api/threads/{id}/replies` accept two optional fields:

```json
{"post_as_user_id":42,"falseflag_reason":"Private reason for attribution"}
```

Only an authenticated, unbanned **administrator** may supply `post_as_user_id`;
moderators/users receive 403 and guests 401. The ID must identify an existing user;
no arbitrary names or new account creation. `falseflag_reason` is required (1–1000
characters). When no attribution ID is supplied, posting is unchanged. The target
can be any existing user, including staff, a banned user or the administrator;
that account is a public attribution, not the source of authorization.

CSRF, PoW, cooldown, rate limits, network restrictions and publication rights are
checked against the **authenticated actor**, not the target. No session switch
occurs. A falseflag post is approved immediately because its actor is an admin.
The chosen user's `auto_approve`, bans, cooldown/proofs and sessions are unchanged.
Root/reply moves, counts, bump/sage and file moderation follow ordinary post rules.

`posts.user_id` becomes the selected public author. All ordinary post/thread/profile/
section/feed responses and the target's `/api/me/posts` therefore show that user,
with their current name, role, avatar and flag. There is no public falseflag marker,
real-author field or change to ordinary API responses. A target account sees the
attributed post in its own message lists; it does not receive the private reason
or actual actor. Attachment names/bytes are not stripped of metadata by this feature.
Existing private IP/browser fields still describe the real request and use existing
admin-only identity access rules. This is not a guarantee of administrator anonymity.

The new `falseflag_posts` table stores post ID, actor ID/name snapshot, target ID/name
snapshot, reason and creation timestamp. It has no HTTP mutation endpoint. The
record is inserted in the post transaction; proof/file/validation failure rolls
back post, private record and cooldown together. Ordinary moderation status deletion
preserves it. It is deliberately separate from moderator-visible `audit_log`, and
not joined into `posts.*` queries. Only GET `/api/admin/falseflags` returns this
paginated log (`page`, `limit`), with thread IDs for links. No moderator access,
no privacy checkbox bypass; account privileges are checked on every request.
Admins may browse this read-only log while their network is in read-only mode.
Backups/DB administrators can access it; retain/protect it like other audit records.

### Markdown presentation

`body` remains raw text in JSON/storage; there is no server HTML field or new body
format parameter. The frontend uses the pinned, locally bundled markdown-it parser
with raw HTML, images and linkification disabled, no user plugins, max nesting 20,
and only HTTP(S), mailto or relative links. Links carry nofollow/noopener/noreferrer.
Headings, emphasis, strikethrough, lists, tables and code are rendered. No syntax
highlighting, remote assets, task-list inputs or raw iframe/embed HTML are enabled.
The site's `>`, `<`, `^` line-prefixes override ordinary Markdown blockquotes and
retain their literal markers plus green/orange/blue styling. Fenced/indented code
is parsed first and is never colored as a quote. Paragraph spacing now comes from
Markdown blocks; raw newlines within a paragraph are rendered as line breaks.
The same renderer applies to existing posts without rewriting their stored content.
Profile descriptions, names, thread titles and compact excerpts are still plain text.

Source: `frontend/markdown.js`; shipped asset: `/markdown.js`. To rebuild:
`npm ci && npm run build:markdown`. Licenses are in `docs/MARKDOWN_LICENSES.txt`.
Keep the shipped asset synchronized with source/lockfile; no npm install is needed
on a production PHP-only server when deploying the committed asset.

## Presentation/public reads and reaction shortcodes

`GET` and attachment `HEAD` requests may include `X-ForBirds-Public-View: 1`.
Except for `/api/session`, the request is evaluated as an unauthenticated reader:
no pending/hidden/rejected content, private counts or moderator-only endpoints.
This is a request-local permission downgrade, not a session change. `/api/session`
retains the actual account/CSRF/privacy/read-only state; `POST` permissions, CSRF,
network restrictions and authentication are unchanged by this header. Responses
remain `no-store`. Ordinary clients that omit the header are unaffected.

The frontend presentation toggle stores `forbirds-presentation` in browser storage,
reloads, requests public data and disables all writes through its API wrapper. It
hides dashboards, private controls and identity/account hints before data loads.
This is screenshot hygiene, not an authentication boundary or anonymizer: public
content and address-bar URLs remain visible. The API remains usable by the real
session outside this UI. Deploy `/presentation.js`, the page heads, CSS, JS and PHP
atomically; no new migration is needed.

Post bodies may contain `:like:`-style reaction shortcodes. Names are exact,
case-sensitive reaction filenames without their raster extension from
`GET /api/reactions`. Duplicate stems resolve to the first catalog entry. Only
catalog-backed local `/static/reactions/…` URLs can become inline images; arbitrary
Markdown images remain disabled. The picker beside formatting help inserts raw
codes at the caret. JSON/storage remain raw text, including unknown codes.
Expansion happens only in Markdown inline text, including formatted text and
colored quotes, never escaped colons, code or link destinations. Missing/removed
catalog files leave codes as text. Profiles, titles and excerpts stay plain text.

## Flash attachments (Ruffle)

Uploads through the existing thread/reply multipart endpoints now accept `.swf`
(case-insensitive extension). The server validates FWS and CWS/zlib containers:
version/header, declared and actual uncompressed length, RECT/frame header and
bounded tag records through End. Maximum uncompressed length: 32 MiB; ordinary
5 MiB/file, 20 MiB/post and 10-file limits still apply. Fake/truncated containers,
size mismatches and ZWS/LZMA return `422`. This is bounded structural validation,
not ActionScript verification or a guarantee of Ruffle compatibility. Requires
PHP zlib; no schema migration.

Each attachment now also includes `is_flash:boolean`. A visible SWF has
`is_flash:true`, `is_image/is_video/is_audio:false`, `preview_url:null` and a
`view_url` of `/api/attachments/{id}/view`. Stored MIME is normalized to
`application/x-shockwave-flash`, but **both `/view` and `/download` serve SWF as
`application/octet-stream`, `Content-Disposition: attachment`**, never plugin
content or HTML. `/preview` returns 404. HEAD/ranges, no-store, nosniff, parent
visibility, premoderation and file/hash bans use the existing attachment checks.

On explicit Start, the parent fetches bytes with the current session (and public
view header in presentation mode), then transfers an ArrayBuffer via a
source-checked postMessage handshake to `/flash-player.html`. The player has an
opaque origin (`sandbox="allow-scripts"`, also enforced by HTTP CSP); it receives
no API URL, tokens or account data. Ruffle's networking, URL opening and script
access are disabled. Stop, spoiler closing and removal of the post destroy the
iframe; already downloaded bytes cannot be retroactively revoked.

The exact pinned local Ruffle JS/WASM assets alone allow CORS `*` so that an
opaque sandbox can fetch its runtime. API/attachment CORS stays disabled. The
player's CSP alone permits `wasm-unsafe-eval` and inline runtime styles; the forum
page keeps its existing script restrictions and permits same-origin frames.
External Flash resources, persistence and website JavaScript integration are not
supported. See README for runtime update/deployment instructions and licenses.

Sidebar disclosure preferences are frontend-only per-section browser storage;
there is no new preference endpoint or change to section API visibility/counts.

## Operator-enabled site updates

- `GET /api/admin/update`: administrator only; returns `enabled`, `maintenance`
  and the latest job (`id`, `status`, `phase`, timestamps, optional `before`/`after`
  commit IDs and a fixed error code). Initial status: `idle`. No raw command
  output, filesystem paths, remotes, actor details or credentials are returned.
- `POST /api/admin/update`: administrator only, ordinary CSRF/network/account
  restrictions, current `password` (12–72 bytes), exact `confirm:"UPDATE"`.
  Extra keys (including branch/remote/command/path) are rejected. At most five
  attempts per five minutes through the normal persistent rate limiter.
  Success: **202**, `status:"queued"`, random job ID. It does not claim the site
  was updated. A single queued/running job or unrecovered maintenance: **409**.
  Bad password: **403**. Disabled by default: **503** (`updates_disabled`).

The HTTP handler only saves a private job and audit event (`site.update.requested`);
it never spawns a process. With `FORBIRDS_UPDATES_ENABLED=1`, an operator-scheduled
native PHP `bin/update.php` worker uses fixed argv commands without a shell:
preflight clean `main`, SQLite VACUUM INTO snapshot, fast-forward-only pull from
`origin main`, then a fresh `PHP_BINARY bin/console.php migrate` process with the
same storage. Migration is never attempted after pull failure. No arbitrary
request-supplied options or automatic merge/stash/reset are supported.

Job states: `idle`, `queued`, `running`, `succeeded`, `failed`. Phases: `queued`,
`preflight`, `maintenance`, `backup`, `pull`, `migrate`, `complete`. Busy worker and
ordinary API requests coordinate through flock; after the maintenance marker is
set, new ordinary GET/POST/HEAD requests fail **503**, including attachments.
The worker drains existing requests before backup/pull. Static assets and GET
`/api/session`/`/api/admin/update` remain available for the administrator status
page, subject to brief SQLite locks. Public-view reads still downgrade identity,
so they cannot access admin status. Presentation mode hides this page entirely.

Pull/migration timeout or failure leaves maintenance enabled for operator repair;
no unsafe automatic rollback is attempted. Crashes require manual examination.
Private snapshot/log/state files are below `storage/site-update/`, outside public;
no new database migration is needed for this feature. Deployment permissions,
cron/Docker setup, OPcache requirements and recovery: **UPDATES.md**.
