# Обновление сайта из панели администратора

Вкладка **«Обновление сайта»** доступна только администратору. Кнопка требует
текущий пароль, явное подтверждение и действующий CSRF. На сервер отправляется
только заявка, а не команды: браузер не выбирает путь, remote, ветку или PHP.
Закрытие вкладки не отменяет принятую заявку. Пароль не сохраняется в задании,
журнале или ответе API. Действие записывается в `audit_log` как
`site.update.requested` с ID задания. Действуют обычные сетевые запреты записи.

**По умолчанию выполнение выключено.** Нет sudo, root-демона, фонового процесса
из PHP-FPM, перезапуска контейнера или автоматической установки cron. Код здесь
не выполняет обновление вашего production-сервера сам по себе.

## Требования и модель доверия

- Обычный Git checkout с директорией `.git`, чистой веткой **main** и доверенным
  `origin`, указывающим на ваш репозиторий. Linked worktrees с `.git`-файлом не
  поддерживаются. Локальные изменения, включая неигнорируемые новые файлы, — отказ.
- Native PHP CLI **8.3+**, те же расширения и **тот же FORBIRDS_STORAGE**, что у
  веб-приложения, Git и неблокирующая интерактивный ввод авторизация для `origin`.
  Node/npm для обновления production не нужны: runtime-ресурсы хранятся в Git.
- Worker запускается **под тем же UID**, что и PHP приложения. Его файлы состояния
  имеют права 0600, каталог — 0700. UID должен иметь необходимые права на checkout,
  `.git`, storage и достаточно места для полного снимка SQLite.
- Это сознательное расширение доверия: если UID веб-приложения может менять код,
  компрометация PHP получает права на deployment. **Не выдавайте sudo, не делайте
  chmod 777 и не меняйте владельца всего проекта вслепую.** Если ваша модель
  безопасности запрещает веб-UID записывать код, оставьте кнопку выключенной и
  используйте отдельную систему deployment/CI с разделением полномочий.
- Используйте read-only deploy key/доступ только на чтение к доверенному origin;
  настройте known_hosts для SSH заранее. Не вводите GitHub-токены в веб-панели.
  Git hooks и fsmonitor отключаются для команд worker, интерактивные запросы
  credentials/SSH запрещены. Защищайте main: полученный PHP-код исполняется при
  миграции с правами приложения.
- Для PHP-FPM включите `opcache.validate_timestamps=1` и
  `opcache.revalidate_freq=0`, либо обеспечьте отдельную корректную процедуру
  сброса OPcache/перезапуска FPM при deployment. Worker CLI не может сбросить
  OPcache другого процесса. С отключённой проверкой timestamps без такой
  процедуры кнопку включать нельзя.
- Не запускайте одновременно другие CLI-миграции/записывающие maintenance-команды.
  Блокировка worker координирует API-запросы и другие экземпляры updater, но не
  произвольные внешние программы.

## Разовое включение

1. Сделайте согласованный внешний backup базы **и всего storage**, включая
   app.key, uploads и avatars. Автоматический снимок ниже — только SQLite,
   не замена резервированию файлов и не универсальный rollback.
2. Проверьте под UID приложения: native PHP, доступ к checkout и origin, чистую
   ветку main, фактический путь storage и конфигурацию OPcache.
3. Задайте `FORBIRDS_UPDATES_ENABLED=1` **в окружении веб-PHP** и перезапустите
   сервис штатным способом, чтобы окружение применилось.
4. Настройте запуск `bin/update.php` раз в минуту под тем же UID, с тем же storage
   и `FORBIRDS_UPDATES_ENABLED=1`. Worker выполняет одну заявку и выходит. Если
   заявки нет — ничего не делает. Два worker одновременно не обновляют сайт.

Пример для обычного сервера в crontab пользователя приложения (замените пути
на реальные; storage должен совпадать с PHP-FPM):

```cron
* * * * * cd /var/www/forbirds && FORBIRDS_UPDATES_ENABLED=1 FORBIRDS_STORAGE=/var/www/forbirds/storage /usr/bin/php bin/update.php
```

Для существующего Docker-layout, в crontab **на хосте** с правом docker exec:

```cron
* * * * * docker exec -u www-data -e FORBIRDS_UPDATES_ENABLED=1 -w /var/www/forbirds forbirds-php php bin/update.php
```

В контейнере должны быть Git, native PHP CLI и доступный checkout с `.git`;
права/SSH/known_hosts настраиваются для `www-data`, не только для root хоста.
Если storage у веб-PHP нестандартный, передайте **тот же** FORBIRDS_STORAGE и
worker. `docker exec -e` влияет только на worker — отдельно включите переменную
в окружении веб-сервиса (например, Compose) и штатно пересоздайте сервис.
Контейнеры с read-only/release-image кодом не поддерживают in-place Git pull:
для них нужен обычный rebuild/redeploy образа, а не эта кнопка.

5. Откройте `/dashboard.html?mode=updates`, введите пароль и подтвердите. Статус
   опрашивается раз в 3 секунды. Ожидание обычно до следующего запуска cron;
   если оно затянулось — проверьте cron/worker, а не нажимайте повторно.

## Что выполняет worker

1. Захватывает эксклюзивную блокировку worker и атомарно берёт единственную заявку.
2. Проверяет checkout, ветку main, отсутствие изменений и наличие origin/базы/key.
3. Создаёт `storage/site-update/maintenance`. Обычные API GET/POST/HEAD получают
   **503**, новые записи не принимаются. До 30 секунд ждёт завершения уже идущих
   API-запросов (включая выдачу вложений), используя файловую блокировку.
4. Создаёт согласованный SQLite snapshot через `VACUUM INTO`, включая committed
   данные WAL: `storage/site-update/backup-JOB_ID.sqlite`, права 0600.
5. Без shell выполняет фиксированную команду (Git options дополнительно отключают
   hooks/fsmonitor и autostash):
   `git pull --ff-only --no-rebase --no-autostash --no-recurse-submodules origin main`.
6. **Только после успешного pull** запускает свежий процесс того же PHP CLI:
   `PHP_BINARY bin/console.php migrate`. Он загружает уже обновлённые PHP/SQL-файлы
   и использует тот же storage. Миграции выполняются и при already up to date.
7. Записывает успешный результат и снимает maintenance. В панели появляется кнопка
   перезагрузки страницы. Ошибки Git/миграций не маскируются успешным результатом.

На Git pull и миграцию — по 180 секунд, команды предварительных проверок — по
30 секунд. stdout/stderr ограничены и сохраняются **только в приватный**
`storage/site-update/job-JOB_ID.log`; API не возвращает их, пути, remote или
credentials. В логах Git всё равно могут оказаться секреты из неправильно
настроенных URL: не публикуйте их. Снимки и логи автоматически не удаляются;
организуйте безопасную ротацию, сохраняя нужные для восстановления копии.

Статика остаётся доступной. GET `/api/session` и GET `/api/admin/update`
оставлены для входившего администратора и страницы статуса; остальные API
закрыты. Страница обновлений не запрашивает ленты/разделы во время обслуживания.
Кратковременная ошибка статуса при блокировке SQLite возможна — панель повторит
запрос. В режиме показа страница и управляющие элементы скрыты.

## Ошибки и восстановление

- `wrong_branch`, `dirty_checkout`, `not_checkout`, `not_installed`: код/данные не
  обновлялись. Исправьте причину вручную; новая заявка допускается.
- Ошибка snapshot/ожидания запросов **до запуска pull**: maintenance снимается,
  если она принадлежит этому заданию; код не изменялся.
- Ошибка/тайм-аут **после начала pull**, ошибка миграции или аварийная остановка:
  maintenance **остаётся**, повторная заявка блокируется. Даже неуспешный Git
  мог частично изменить файлы. Автоматического rollback нет: частично применённые
  миграции нельзя безопасно отменить одним Git-командой.
- Если процесс погиб до установки maintenance, состояние может остаться running,
  но прежний сайт продолжит работу. Для новой заявки всё равно нужно проверить
  состояние на сервере и сбросить зависшую запись вручную.

Порядок действий оператора:

1. Остановите cron/timer worker и выключите веб-обновления. Убедитесь, что живого
   worker и его дочерних процессов Git/PHP больше нет. **Не снимайте блокировку
   с работающего обновления.** Maintenance пока не удаляйте.
2. Прочитайте приватные state.json и log, проверьте текущий Git HEAD и migrations.
   Исправьте права/доступ или восстановите согласованную версию кода, БД и файлов
   из backup в зависимости от стадии сбоя. Не удаляйте действующую БД и не
   подменяйте её случайной копией. Сохраняйте повреждённое состояние для разбора.
3. Тем же UID/PHP/storage успешно выполните `php bin/console.php migrate`, проверьте
   согласованность кода/схемы, OPcache и приложение. После ремонта, при остановленном
   worker и выключенных веб-обновлениях, сохраните state.json для истории и удалите
   **только** `site-update/state.json` и `site-update/maintenance`. Снимки, ключ,
   базу и uploads не трогайте. Само наличие lock-файлов нормально: flock снимается
   ОС при завершении процесса, удалять lock-файлы не нужно.
4. Возобновите обычную работу, затем при необходимости верните opt-in и timer.

Новая миграция схемы для самой кнопки не требуется. Все пути очереди приватные и
не должны выдаваться веб-сервером напрямую; document root остаётся `public/`.
